---
name: crap-operational-review
description: Review imported workload evidence for separate scalability, performance and reliability scores, compare operational runs, and identify source risks requiring measurement. Use for operational health and SLO reviews; ordinary CRAP cleanup uses crap-development-review.
---

Use the connected MCP tools by their base names; clients may prefix them. On a macOS machine installation, run `bash ~/.local/share/crap-mcp/current/scripts/ensure-service.sh` before connecting. For a foreground installation, probe its documented health endpoint and start the local service if needed. Register the absolute Git checkout path with `register_project` and use that project ID throughout.

Read `get_project_settings` and `get_operational_scorecard({project,format:"data"})`. The latter returns the repository identity and active policy hash used by evidence import. A project without a policy or imported evidence is unmeasured. Do not infer operational scores from function CRAP, passing builds, source scans or configured concurrency limits.

For a new workload, define version 1 `settings.operational`: named workload/profile, freshness and duration limits, confidence, enabled source rules, and three independent metric lists. Each nonempty axis requires positive weights summing to one and a mandatory SLO. Metric targets, failure thresholds, units, statistics and minimum samples must be chosen before measuring. Use `update_project_settings` with the current settings revision, the full settings and a rationale. Preserve unrelated settings. On conflict, reload and merge. The dashboard's Operational health settings edit the same policy; Team manifest exports it for other checkouts. Proposed thresholds and weights need workload-specific calibration, not automatic acceptance as standards.

Import only content-free aggregate evidence through `import_operational_evidence`. Check the artifact's exact source commit, repository, image/config/policy hashes, workload/dataset/harness, environment/resources, mode, collection interval, attempt counts, metric populations, confidence assumptions and gates. Use the installed repo's `docs/operational-health.md` for the v1 contract and examples. Failed harnesses must be imported as failed, with no invented measurement. Distinguish synthetic/local/development/staging/production observations. For measured executions, mode identifies the workload environment, not the collector's location: development logs extracted on a laptop remain `development`, not `local`. An older strict server may reject `development`; update it rather than relabeling evidence. Missing telemetry remains incomplete even if extraction succeeds. Do not silently rewrite provenance fields to make an incompatible artifact import successfully.

For new imports include optional v1 `provenance` with `suite`, `appBuild` (nullable for server-only runs), `routingHash`, `sourceTreeHash`, and `stage` (`worktree` or `integrated`). Supply the actual deployed image digest in `imageHash`; it may be null only with an app build identity. These are observed identities, not guesses or current defaults. Existing v1 evidence without provenance remains readable with its original ID, but cannot become a tagged baseline. Import a newly tagged observation rather than editing an old snapshot.

Save the returned immutable snapshot ID before a change. Read `get_operational_baselines` and call `set_operational_baseline` with the snapshot, returned baseline revision and reason. This appends a selection; it does not erase earlier selections or turn missing measurements into scores. Worktree selections remain provisional. After integration, rerun the same workload against the exact integrated source/build/configuration, import it with `stage:"integrated"`, and select it as a new baseline. The source must equal the current configured integration ref; ancestry alone is insufficient. Retain the earlier snapshot for comparison. Reload on a baseline revision conflict; never overwrite another agent's selection. Baselines are local to the registered checkout.

`scan_operational_risks` supplies advisory source patterns and verification recipes, not measured runtime failures. Trace input bounds, ownership and reachability before recommending a repair. Keep omissions and unsupported languages explicit. It currently checks direct pg Client construction in functions and Promise.all over map; it does not perform comprehensive infrastructure analysis.

A score request authorizes reading evidence, not starting production traffic, load tests, fault injection or cloud changes. Run a harness only when the user's task authorizes that work and environment. Count failed, slow and incomplete initial attempts; separate legitimate user cancellations from errors. Never average percentiles. Preserve per-cohort histograms, all-attempt denominators and the independence assumptions of confidence-bounded rates. No benchmark result from a failed harness qualifies.

After an authorized change and separately run measurement, import the new evidence. Call `review_operational_changes` with both snapshot IDs and `format:"markdown"`. A configuration experiment requires `allowConfigChange:true` only when that is the intended change; explain it. Incompatible workload, policy, resources, model, corpus, duration, populations, offered demand or fault cases suppress deltas. Source/image/deployment changes are listed. Integrated code requires a fresh run; ancestry does not transfer measurements to a different revision. Repeated comparable observations are needed for speed claims or causal attribution.

Render the returned score heading and tables directly in chat. Preserve all three axes, raw measurements, evidence counts, provisional bounds and qualification reasons. A high weighted score does not override a failed mandatory SLO or integrity gate. Do not combine the axes into a headline average. Link the selected dashboard. If code was edited, also finish the ordinary development review against its saved CRAP snapshot and report its independent grade.
