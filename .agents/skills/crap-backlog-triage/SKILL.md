---
name: crap-backlog-triage
description: Use a connected CRAP Score MCP server to choose a repository maintenance task from language-specific anti-patterns, complexity, nesting and test coverage.
---
Use the connected MCP tools by their base names below; clients may prefix them with the server name. On a macOS machine installation, before connecting run `bash ~/.local/share/crap-mcp/current/scripts/ensure-service.sh`. It checks the local service and starts the installed launch agent if necessary. For a foreground installation, probe its configured /health endpoint and start the documented machine command if offline. Retry the MCP connection after it becomes healthy.

On the machine service call `register_project` with the absolute output of `git rev-parse --show-toplevel` from the active checkout. Use the returned ID as `project` on every analysis call, including pagination and the final review. The project picker at http://127.0.0.1:47731/ lists registered checkouts. If only the legacy stdio tools are available, verify their configured checkout before use.

Read `get_project_settings` and compare the enabled packs and linters with the source files in scope. Before the baseline, check `swiftlint version` for Swift sources and `ruff --version` for Python sources in the shell that will run the project check. Activate the project's virtual environment first if it provides Ruff. For each available tool whose linter is disabled, call `set_project_language({project, language, enabled:true, linter:true, revision})` with `swift` or `python`. Use the revision returned by the first update for the next one. Swift has a core parser. The same call enables the optional Python parser. If a linter is missing, report the gap and continue with the available tools. Enable other needed optional parsers before taking the baseline. On a revision conflict, reload settings and reapply the intended change.

For a foreground service use its built `dist/project-check.js` in place of the installed checker path. Run `node ~/.local/share/crap-mcp/current/dist/project-check.js "triage baseline"` from the target checkout. Include additional repository-required checks as needed. When coverage is unconfigured, run the normal tests and report missing scores. Consult recent outcomes in `get_project_settings` to identify recurring failures and successful fixes from comparable runs. Cite the suite, policy and observed evidence behind the selected task.

Call scan_repository_hotspots; inspect completeness, skipped files, suite and commit. Use view=integration for the shared baseline, or the worktree view for local changes. Page by nextOffset. Start with score order. If requested, prioritize churn (file-level changes over 90 days) or critical paths. Query coverage=unscored separately so missing evidence remains visible.

For actionable fixes, call `scan_code_patterns` on the worktree. For subsequent pages pass its `snapshot` and `nextOffset` as `offset`. Cite the rule, file, line, and suggested fix, including findings outside functions or without coverage. Summarize the grouped spacing count separately. For Python, inspect Ruff's diagnostics in the project-check output and its exit status in the check's `tools` list.

When a candidate maps to a function, inspect it with analyze_function_health. Cite its location, observed trigger and completion check; line coverage alone doesn't identify a missing behavior. Carry the worktree snapshot into development review and include the hotspot finding ID when one exists. Only publish a selected issue when asked, using the explicit CLI in the README. Use a plain issue reference in a PR so the integration scan controls closure.
